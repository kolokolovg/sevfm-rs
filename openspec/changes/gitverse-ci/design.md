# Design

## Context

Мотивация — proposal.md («Why»). Ограничения, определившие подход:

- Раннеры GitVerse: только `ubuntu-latest` (документировано), Docker без
  состояния между запусками, дефолтный таймаут джобы 15 минут, месячный
  бюджет сборочного времени. Полный прогон сегодняшнего CI там ~13 минут
  (сборка зависимостей с нуля дважды: clippy в check-режиме + тесты
  с кодогенерацией).
- Оба падения CI — тесты семейства «публикация по звучанию»: юнит-тест
  пайплайна и интеграционный ICY-тест. Продукт работал как задумано —
  рушились предположения тестов о планировщике потоков.
- `permissions`, `concurrency`, `repository_dispatch` в справочнике
  синтаксиса GitVerse отсутствуют; `Swatinem/rust-cache` не подтверждён
  и живьём не сработал ни разу (0–2 с, артефакты не восстанавливаются).

## Goals / Non-Goals

**Goals:**

- Тайминг-тесты семейства «публикация по звучанию» — детерминированные
  относительно скорости планировщика: зелёные и на быстрой машине, и на
  перегруженном раннере.
- Отдельный воркфлоу для GitVerse: только документированные возможности,
  укладывается в 15 минут с запасом, зелёный без поблажек (retry нет).
- Диагностируемость: при тайм-ауте интеграционного теста в панике виден
  stderr ребёнка.

**Non-Goals:**

- Не ускоряем GitHub-CI и не меняем его ворота — он остаётся полным
  (fmt + clippy + тесты + windows-сборка).
- Не добавляем кэширование на GitVerse (лимиты `actions/cache` не
  опубликованы; ~9 минут укладываются в бюджет — вернуться, если станет
  тесно).
- Не чиним другие тесты и не вводим retry/повторы прогонов — маскировка
  вместо устранения.
- Windows-сборка на GitVerse (self-hosted раннер) — вне scope.

## Decisions

### D1: Юнит-тест — решения по измеренному `sound_pos`, не по кадрам

`metablock_publishes_by_sounding_not_by_decoder_readahead` сейчас
предполагает, что к первому ассерту прозвучало ~25 кадров (~10 КиБ):
цикл «ждём запаса декодированных кадров» (`while source.packets() < …`)
потребляет сэмплы, не считая их. На быстрой машине декодер обгоняет
потребителя и ожидание дешёвое; на голодной — цикл «съедает» десятки
кадров, звучащая позиция легально доходит до метаблока 16 КиБ, гейт
честно публикует трек — ассерт «ещё не опубликовано» видит опубликованный.

Новый каркас: пороги в байтах против атомика `sound_pos`, который
обновляет **только потребитель** (один store на границе чанка,
`Iterator::next`; декод-поток в него не пишет — проверено ревью по
исходнику), поэтому пороги читаются без гонки:

1. Потребляем сэмплы, пока измеренный `sound_pos < 8 КиБ` (половина
   границы — запас против скачка метки через границу: шаг метки ≤ окно
   пейсера + кадр ≈ 2.5 КиБ); дренаж гейта; ассерт «трек не опубликован».
2. Потребляем, пока `sound_pos ≥ 16 КиБ` не измерен; дренаж; ассерт
   «трек опубликован» (записи трёх метаблоков идентичны — прыжок через
   несколько безопасен, `drain_until` отдаёт последнюю).
3. Ассерт окна пейсера: `sound_pos ≤ границы + LEAD_BUDGET_BYTES`
   (литеральные 8 КиБ, как раньше) — метка потреблённого чанка не
   указывает дальше окна пейсера от звучания.
4. Фаза 3b — тот же ассерт на второй границе (32 КиБ): без пейсера MSS
   тянет блоки с удвоением до 32 КиБ, к звучанию 32 КиБ метка ~63 КиБ —
   запас детекции ~22 КиБ против ~7 КиБ у первой границы (живая
   проверка: при отключённом пейсере фаза 3 падает с sound_pos=31744).

Счётчик кадров и арифметика «2304 сэмпла/кадр, 384 Б/кадр» удалены
полностью. Альтернатива — считать сэмплы в цикле ожидания и
пересчитывать пороги в кадрах: отвергнута, всё ещё связывает ассерты
на предположения о темпе декодера — те же, что уже стреляли.
Измеренная позиция — единственная величина, по которой гейт реально
публикует.

Ограничение: `next()` может возвращать тишину для ещё не декодированных
кадров — тишина `sound_pos` не двигает, поэтому циклы (1)–(4) имеют
дедлайн прогресса с диагностикой (sound_pos, кадры, исход тракта) и
уступают CPU (сон 1 мс каждые 4096 сэмплов — без уступки поток теста
конкурирует за ядро с декод-потоком, которого ждёт). Фикстура целиком
в кольце, декод — чисто CPU-шный, прогресс гарантирован.

Нюанс шкал (только теста, не продукта): кольцо теста получает framed
вместе с метабайтами — `sound_pos` их считает, а offset'ы гейта чисто
аудио; в продакшене framer вырезает метабайты до кольца и шкалы
тождественны. Направление безопасно (инфляция звуковой шкалы публикует
раньше на ~сотни байтов против допусков в КиБ).

### D2: Интеграционный тест — диагностика + дедлайн 60 с + живой дедлайн чтения

`icy_metadata_printed_to_stderr`: при провале `.expect` на Option сейчас
не показывает ни одной строки ребёнка. Исправление по образцу остальных
тестов файла (они включают `{stderr}` в ассерты): собирать прочитанные
строки и включать их в паники станции и трека. Дедлайн 30 с → 60 с —
согласован с бюджетом `endless_garbage_stream_exits_with_code_2`
(60 с, тот же аргумент: узкое место — не сеть, а темп раннера).
Аудио-путь на раннерах GitVerse рабочий (прогон №1 — весь набор
зелёный), значит запас по времени — правильная реакция на голод CPU,
а не маскировка.

Плюс механика дедлайна (находка ревью): блокирующий `lines()` проверял
дедлайн только между строками — молчащий живой ребёнок (заклинивший
пайплайн без строк и без EOF) висел бы вечно. Чтение вынесено в поток
с каналом `recv_timeout(остаток дедлайна)`: тайм-аут убивает ребёнка
и паникует с дампом; EOF отключает канал и даёт панику с дампом
последних слов. Дополняется джобовым `timeout-minutes: 30` в linux-джобе
GitHub-CI (дефолт платформы 360 минут) — страховка от неизвестных
классов зависаний.

### D3: Воркфлоу GitVerse — минимум документированного

`.gitverse/workflows/ci.yml`: `push` по веткам + `workflow_dispatch`
(кнопка требует файл на main — будет), одна джоба `ubuntu-latest`,
`timeout-minutes: 15`, шаги повторяют проверенные живьём прогоны:
checkout@v5 → dtolnay/rust-toolchain@stable → apt-зависимости (alsa,
xkbcommon, fontconfig — линковка) → `cargo fmt --all --check` →
`~/.asoundrc` null-PCM → `cargo test`. Без clippy (двойная сборка
зависимостей; полный набор ворот — GitHub на тех же коммитах), без
кэша, без `permissions`/`concurrency` (не документированы), без
windows-джобы (нет раннеров — вечное waiting). Триггер `pull_request`
сознательно не включён: GitVerse поддерживает его частично, репозиторий —
личное зеркало, PR живут на GitHub; PR из веток того же репо покрыты
`push: branches: ['**']`.

Альтернатива «не переносить, а чинить приоритет у `.github`» отвергнута:
`.github/workflows` — бонус совместимости с оговоркой про `.yaml` в доках,
родной путь — `.gitverse/workflows`; отдельный файл также даёт независимые
ворота под возможности платформы.

### D4: Переключение источника — руками пользователя, с проверкой Pages

Настройка «приоритет для пути для конфигурационных файлов workflow»
переключается в веб-морде (Настройки → Репозиторий). По FAQ приоритет
действует при существовании обеих директорий — после коммита
`.gitverse/workflows/ci.yml` обе существуют. Побочные эффекты считать
фичей: `release.yml` и windows-джоба на GitVerse больше не срабатывают.
Риск — Pages: воркфлоу `build-and-deploy-pages.yaml` на gh-pages обязан
остаться достижимым; если он в `.github/workflows` на той ветке —
зеркалировать в `.gitverse/workflows` той же ветки (задача с проверкой).

## Risks / Trade-offs

- [Допуски D1 слишком широкие/узкие — тест всё ещё чувствителен] →
  стресс-верификация: ≥10 прогонов набора под искусственной переподпиской
  CPU (taskset) и без неё; пороги берутся из констант тракта
  (`PACED_READ_BYTES`, `LEAD_BUDGET_BYTES`), а не из новых магических чисел;
  ловушка пейсера доказана исполнением (отключение пейсера красит фазу 3
  с sound_pos=31744 против бюджета 24576, фаза 3b добавляет запас до ~22 КиБ).
- [GitVerse-воркфлоу уложится впритык к 15 мин в плохой день] →
  без clippy ожидание ~8–9 мин (худший наблюдённый день ~12 мин для
  вдвое большей работы); таймаут зафиксирован явно, падение по таймауту
  видно сразу, а не висит. Критерий пересмотра: ≥2 падения по джобовому
  таймауту за месяц → поднять до 20 мин (в пределах документированного
  максимума 30 мин, с оглядкой на месячный бюджет).
- [Коммит, живущий только на gitverse, не получает clippy вовсе] →
  процессное правило: пуш в gitverse — после зелёного прогона GitHub
  того же коммита; clippy — ворота качества, не корректности, тесты
  на GitVerse остаются.
- [После переключения приоритета Pages-деплой молча перестанет срабатывать]
  → проверено: воркфлоу Pages в репозитории отсутствует, деплой
  обслуживается платформой (actor `gitverse-actions`) — переключение
  приоритета пути на него не влияет; живой контроль следующего деплоя
  в follow-up.
- [По docs приоритет может значить «обе директории, но с приоритетом»,
  а не «только одна»] → первый же пуш после переключения проверяем:
  в CI/CD должен появиться только прогон нового воркфлоу; дубль —
  откат настройки до разбирательства.
- [Шкалы offset'ов гейта (чистое аудио) и кольца (в тесте — с
  метабайтами) разойдутся при будущих проверках метаблоков №2+] →
  задокументировано в D1 (нюанс шкал): в продакшене шкалы тождественны,
  рассинхрон — артефакт тестовой сборки framed.

## Migration Plan

Коммит с тестами и воркфлоу (пуш — по явному указанию пользователя) →
пользователь переключает приоритет пути в веб-морде GitVerse и отменяет
висящий прогон №5 → пуш в gitverse → контроль: только новый воркфлоу,
зелёный, ~9 мин; Pages на gh-pages живой. Откат — вернуть приоритет
на `.github/workflows` (файлы `.github` не удалялись).
