# Design

## Context

Кеш обложек — плоский каталог `<XDG_CACHE_HOME|~/.cache>/sevfm/covers` с файлами `<sha256(artist|title)>.jpg` (сырые байты CDN, медиана 108 КБ). Весь кеш-контур в `src/cover.rs`: `read_cached`/`write_cached`/`sweep_stale_temp_files`; воркер один (`worker_loop`), работает и в UI, и в headless. Замер (2026-11-04): приток ~8 МиБ/день. Мотивация — proposal.md. Требования — дельта `album-art`.

## Goals / Non-Goals

**Goals:**
- Жёсткая граница размера кеша при бесконечной ротации станции; любимцы ротации вытесняются последними.
- Ручной рубильник `--clear-cache`, работающий в том числе на Windows GUI-бинарнике.

**Non-Goals:**
- Настраиваемость лимита (конфиг-файла нет, CLI минимален — константа; расширение — будущим change'ом).
- In-memory LRU-слой, сжатие или перезапись обложек (в кеш пишутся исходные байты — без изменений).
- Чистка чужих/старых каталогов (`sevfm-radio` снесён вручную; публичные релизы всегда писали в `sevfm/`).

## Decisions

### D1. LRU по mtime файла, touch при попадании
Время последнего использования — mtime файла записи: при hit `read_cached` обновляет его, вытеснение сортирует по mtime. `std::fs::File::options().write(true).open(..)?.set_modified(now)` — std, edition 2024, без новой зависимости. Отказ touch (файл read-only, Windows-шеринг) — тихий пропуск: политика деградирует до FIFO, поведение остаётся корректным.

Альтернативы: индекс-файл со счётчиками (новое состояние, синхронизация, повреждения); atime (на Linux повсеместно `noatime`/`relatime` — ненадёжно); отдельная БД (несоразмерно задаче).

### D2. Лимит 100 МиБ, константой
`CACHE_LIMIT_BYTES = 100 МиБ` рядом с `STALE_TEMP_AGE` с комментарием-обоснованием замера. При темпе станции ≈ 950 записей ≈ две недели уникальных; вытеснение затрагивает лишь хвост, повторные треки остаются в кеше.

Альтернативы: TTL по возрасту (не гарантирует потолок при темпе ~8 МиБ/день: 30 дней ≈ 240 МиБ); лимит числа записей (менее предсказуем — размеры 29–387 КБ); CLI/env-параметр (расширяет поверхность запуска ради однократной настройки).

### D3. Точки проверки: старт воркера + порог прироста
Проверка выполняется (1) при старте `worker_loop` сразу после `sweep_stale_temp_files` — покрывает перезапуски и стартует долгие сессии с чистого листа; (2) в работающем воркере — после того как с прошлой проверки записано `CACHE_RECHECK_DELTA_BYTES = 8 МиБ` новых обложек (примерно дневной приток). Без таймеров и дополнительного потока: скан `read_dir` ~1000 файлов — миллисекунды, в потоке воркера между треками.

Альтернативы: проверка после каждой записи (ненужные сканы), выделенный поток-уборщик (новая сущность и гонки ради миллисекундной работы).

### D4. Механика вытеснения
`enforce_cache_limit(dir, limit)`: собрать `(путь, mtime, размер)` регулярных файлов `*.jpg`; если сумма больше лимита — удалять по возрастанию mtime, пока сумма не уйдет в лимит; итог — одна запись в лог («превышен лимит: удалено N файлов, X МиБ»). Отказ удаления отдельного файла — запись в лог, продолжить со следующего. `*.tmp` не трогаем: свежие могут принадлежать параллельному экземпляру (суффикс pid), осиротевшие уже убирает существующий sweep. Параметр `limit` — тестируемость политик малыми числами; продакшн-значение передаёт вызов.

### D5. Флаг `--clear-cache`: разбор и ранний выход
`parse_args` (стиль `--headless`): флаг `--clear-cache`, повтор — ошибка; сочетание с позиционным URL или `--headless` — ошибка «флаг --clear-cache не сочетается с другими аргументами», код 2, кеш не тронут (разбор раньше действия). `Launch` получает поле `clear_cache`. В `main.rs run()` — сразу после разбора, до attach-консоли, связки окна и воркера: `clear_cover_cache()` → печать объёма в stdout → `EXIT_SUCCESS`. На Windows условие `attach_console_for_headless` расширяется до `headless || clear_cache` — вывод утилитного запуска обязан быть виден.

`pub fn clear_cover_cache()` в `cover.rs`: удаляет регулярные файлы (`*.jpg` и `*.tmp`) в собственном каталоге кеша, каталог оставляет; отсутствующий каталог — `(0, 0)`. Печать и форматирование объёма — в `main.rs`, библиотека возвращает числа. Частичная неудача удаления (находка ревью): библиотека возвращает и число неудач, бинарник печатает предупреждение в stderr и выходит кодом 2 — тихий успех при несостоявшейся очистке вводит в заблуждение.

### D6. Текущая обложка не защищается от вытеснения
Отдельный «grace» для файла текущего трека не вводим: свежоиспользованная запись и так последняя в порядке удаления, а MPRIS-клиент с уже полученным `file://` на вытесненный файл просто не перечитает арт (безвредно; повтор трека перепоискает). Меньше ветвления — честнее политика.

## Risks / Trade-offs

- [Touch отклонён ОС (read-only, шеринг)] → тихий пропуск, LRU деградирует до FIFO — поведение остаётся корректным, лога не требует.
- [Вытеснение обгоняет медленный MPRIS-клиент] → клиент показывает арт без обложки; повтор трека восстанавливает. Принято (D6).
- [Два экземпляра приложения чистят один каталог] → конкурентные unlink/touch атомарны и безвредны; `.tmp` другого экземпляра не трогаем (D4).
- [Скан каталога в потоке воркера] → миллисекунды на ~1000 файлов, частота ограничена порогом 8 МиБ (D3); поиск обложек не блокируется ощутимо.

## Migration Plan

Новое поведение, миграции нет. Откат — revert коммита; состояние кеша после отката просто снова растёт без ограничения.
