## Workflow follow-up

- Ревью субагентами (hunter + oracle + security) выполнено 2026-11-04. Устранены: P2 — нечитаемый каталог кеша молча трактовался как пустой (`clear_cover_cache_in` различает `NotFound` от прочих ошибок, возвращает число неудач, бинарник при `failed > 0` выходит кодом 2 с предупреждением — design D5 дополнен); P2 — тихая смерть границы размера при нечитаемом каталоге в `enforce_cache_limit` (одна строка в лог); P3 — ложный «не удалось удалить» при гонке (NotFound = уже удалено = успех, в обеих чистках); security LOW — симлинки в каталоге кеша: `DirEntry::metadata` — lstat-семантика, ссылки не собираются/не удаляются/не следуют, `touch_last_used` не открывает ссылки; P3 — ветка ГиБ в `format_bytes` (легаси-кеши без лимита), неверный комментарий теста `--clear-cache`; oracle — out-параметр `&mut u64` заменён структурой `CacheGrowth` (порог параметризован, тесты границы и сброса без 8 МиБ фикстур). Принято: `--clear-cache` удаляет и свежие `.tmp` параллельного экземпляра (D4 ограждает только вытеснение; страдает собственный процесс, best effort); эскалация жертв при stuck-файлах соответствует спеке («вытеснение продолжается остальными»); путь каталога в выводе не печатается (не расширять публичный API ради косметики); между проверками кеш может достигать ~лимит+18 МиБ — спека ограничивает «при проверке». Вердикт security: удаление за пределы каталога кеша невозможно (read_dir без `..`, имена — sha256), инъекции в терминал закрыты `sanitize_for_terminal`, DoS между проверками ограничен лимитом тела 10 МиБ.
