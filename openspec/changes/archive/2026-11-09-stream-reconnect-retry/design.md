# Design

## Context

Классификация отказов в reader-цикле (`src/net.rs:602-625`): сетевые ошибки запроса (`StreamError::Request` — DNS/TCP/TLS/таймауты) и HTTP 5xx идут в transient-путь — печать причины, `set_net_status(Reconnecting)`, лестница backoff 1→2→5→10 с без лимита попыток; HTTP 408/429 повторяемы с v0.1.4 (design D4 `harden-network-resilience`); остальной 3xx/4xx (`(300..500).contains(code)`) — `mark_fatal()` и завершение reader'а → `SessionOutcome::Fatal("подключение отклонено сервером")` (`session.rs:316,401`) → красная рамка UI / ненулевой код headless. Различение «первое соединение vs переподключение» в коде уже есть: `ReaderState::had_connection` (`net.rs:511`) — false до первого прочитанного байта, true после (`net.rs:767`); сегодня флаг используется только для выбора слова «подключение»/«переподключение» в логе и статуса. Спецификации `audio-pipeline` («Ошибки запуска») и `player-ui` («Фатальные ошибки сессии») закрепляют перманентность отказа без различения первого и повторного соединений.

## Goals / Non-Goals

**Goals:**
- Отклонение сервера (HTTP 3xx/4xx) на повторном соединении живой сессии приравнять к сетевой ошибке: transient-путь, существующая лестница backoff, сессия продолжает жить.
- Сохранить мгновенную диагностику ошибочного адреса: перманентный отказ только на первом соединении сессии.

**Non-Goals:**
- Ретраи 3xx/4xx на первом соединении — неверный маунт должен диагностироваться сразу, а не крутиться вечно в «Подключении».
- Лимит попыток или автоостановка после N отказов — контракт остаётся как у сетевых ошибок: до остановки пользователем/сигналом.
- HTTP-код в тексте красной рамки — пользователь выбрал только ретраи; код остаётся в stderr.
- Следование редиректам стрим-агентом — по-прежнему `max_redirects(0)` (design D4 `harden-network-resilience`).

## Decisions

### D1: Граница фатальности — существующий флаг `had_connection`
Условие перманентности `StreamError::Status` в `reader_loop` дополняется `!state.had_connection`: фатален только отказ первого соединения. Новых состояний, полей и аргументов нет — флаг уже несёт ровно эту семантику (первый прочитанный байт = соединение было рабочим) и живёт в той же функции. Граница байтовая, а не по TCP-соединениям: 200-ответ, закрывшийся без единого байта тела, успешным не считается — отказ следующего соединения остаётся фатальным (пин-тест `empty_200_then_status_stays_fatal`; находка ревью oracle).
*Обоснование*: до первого соединения 4xx почти всегда ошибка адреса (несуществующий маунт в позиционном URL); стартовая валидация URL (`ui.rs`, D5 `harden-network-resilience`) проверяет только синтаксис и отличить несуществующий маунт не может — мгновенный отказ сохраняет наблюдаемость запуска. После первого байта данных URL доказан рабочим, отказ повторного соединения на практике транзиентен (перезапуск icecast, пропавший на секунду маунт, ответ узла цепочки прокси).
*Альтернатива*: различать по коду статуса (403 — ретрай, 404 — фатал) — отвергнута: не отличить «маунта нет» от «маунт на секунду пропал», наблюдаемый код отказа после обрывов неизвестен (в stderr UI-режима не попадал).

### D2: На переподключении — единое правило «любой статус отклонения повторяем»
При `had_connection` любой `Status(code)` (3xx/4xx, включая 408/429) идёт общим transient-путём: печать причины, `set_net_status`, лестница backoff. Отдельная ветка для 3xx («сервер переехал») не вводится: редиректы стрим-агентом не следуются, переезд URL станции решается перезапуском сессии с новым адресом, а комбинаторика веток ради редкого случая не окупается. Отдельная формулировка лога тоже не вводится (см. D3).
*Обоснование*: единое правило проще проверить тестами (таблица кодов на первом/повторном соединении), оно совпадает с уже реализованным поведением 408/429. Вежливость к серверу гарантирует существующая лестница — плато 10 с ≈ 6 запросов в минуту.

### D3: Диагностика — общий transient-путь без новых формулировок
Отказ на переподключении печатается действующей строкой transient-пути: `подключение не удалось: {e}`, где `StreamError::Status` уже рендерится как `стрим недоступен: HTTP {code}` (`net.rs:105`), плюс штатная строка `переподключение через {delay} (попытка N)`. HTTP-код виден в stderr точно так же, как у 408/429 сегодня. Строка `сервер отклонил запрос: HTTP {code} — повторение бессмысленно` остаётся только у фатала первого соединения. Красная рамка не наступает (исход сессии не Fatal); статус UI уже переводится в «Переподключение» через `set_net_status` по `had_connection` — правок UI не требуется.

## Risks / Trade-offs

- [Станция переехала навсегда — 3xx/4xx на каждом переподключении] → клиент остаётся в «Переподключении» неограниченно долго, вежливо по 10 с; HTTP-код виден в stderr, остановка — «Стоп»/сигнал, новый адрес — перезапуск сессии. Осознанный обмен непрерывности против автоостановки (запрос пользователя).
- [Прокси-цепочка пользователя отвечает 4xx постоянно] → то же поведение: ретраи, не крах; сценарий пользователя (обрыв сети) как раз заканчивается восстановлением.
- [Флаппинг: чередование 200 и отказов] → каждая неудача поднимает индекс лестницы, первый прочитанный байт сбрасывает (`net.rs:766`) — шторма запросов нет, лестница саморегулируется; худший случай ≤1 запроса/с (находка ревью security).
- [Отличить регресс фатала первого соединения] → интеграционный тест `permanent_status_terminates_reader_with_fatal_flag` (таблица расширена в этом change до 301/403/404) фиксирует границу D1 слева; справа её держит `rejected_reconnect_retries_and_streams` (403/404/301 на переподключении) и пин-тест байтовой границы `empty_200_then_status_stays_fatal`.
- [Отказы длятся дольше 30 с после 200-с-байтами, но до первого распознанного кадра] → сессия завершится `Fatal("воспроизведение прервано ошибкой тракта")` (лимит первого кадра), а не точным «подключение отклонено сервером»; окно практически мертво для живого радио (кадр находится в первых килобайтах), HTTP-код остаётся в stderr (находка ревью hunter).
- [Вечный отказ переподключения — stderr-спам] → две строки на попытку (~12 строк/мин при плато 10 с); тот же контракт, что у существующего ретрая сетевых ошибок, память не растёт (находка ревью security).

## Migration Plan

Чистая правка одной ветки `reader_loop` в `src/net.rs` + тесты; данных, форматов и интерфейсов нет. Откат — реверт коммита; взаимодействующих состояний нет.

## Поведение простыми словами

Если сессия хоть раз сыграла, любой ответ сервера «нет» (403, 404, редирект — что угодно) при восстановлении лечится так же, как обрыв сети: подождать 1, 2, 5, потом по 10 секунд и пробовать снова, сколько угодно долго, пока пользователь не остановит. Красной рамки и остановки больше не будет — статус «Переподключение», а когда сервер снова примет запрос, музыка вернётся сама. Если же «нет» пришло на самом первом знакомстве с адресом — это по-прежнему ошибка запуска: сообщение и остановка, потому что вероятнее всего опечатка в адресе потока.
